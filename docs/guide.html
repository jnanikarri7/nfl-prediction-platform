🏈 NFL Prediction Platform — Learning Guide

A section-by-section walkthrough of the concepts and code. Read top-to-bottom to learn, or jump via the contents. Each part explains what, why, alternatives, and next steps.

0 · Overview & the big idea

We predict NFL game outcomes (who wins, by how much, and vs. the Vegas spread) using a modern lakehouse + MLOps stack. The whole pipeline runs $0 locally and is ready to run on Azure Databricks for <$5/month.

Core thesisNFL data is wide but small (~550k plays, ~250 MB). The hard problems are temporal correctness (never letting the future leak into the past) and honest evaluation against the betting market — not big-data scale. The win condition is matching the market and being well-calibrated, not "beating Vegas" (which public models can't reliably do).

Data flow (Medallion architecture):

nflreadpy ─▶ 🥉 Bronze (raw+lineage) ─▶ 🥈 Silver (clean+validated) ─▶ 🥇 Gold (features) ─▶ 🤖 MLflow (models)
                                                                                           └▶ 🎰 vs Vegas baseline

1 · Concept primer learn these first

ConceptPlain-English meaning
LakehouseCheap cloud object storage (files) + a table layer that gives database-like guarantees on top.
Delta LakeThe table format we use. Adds ACID transactions, versioning/time-travel, and schema enforcement to Parquet files.
Medallion (Bronze/Silver/Gold)A 3-tier refinement pattern: raw → cleaned → feature-ready. Each layer has a clear contract.
EPA (Expected Points Added)How much a single play changed the team's expected points. The core "goodness" signal in modern NFL analytics.
CPOECompletion % Over Expected — passing accuracy adjusted for difficulty.
Elo ratingA single number for team strength, updated after each game by how surprising the result was.
Data leakageAccidentally using information not available before kickoff. Inflates test scores; collapses in production. The #1 enemy.
Walk-forward CVValidation that respects time: train on past seasons, test on the next. (Never random k-fold.)
CalibrationWhen you say "70%," it happens 70% of the time. Measured by Brier / log-loss, not accuracy.
Market anchoringStart from the Vegas line (which already encodes huge information) and only deviate where you have real signal.

2 · Infrastructure & cost (Phase 1)

What: Terraform provisions ADLS Gen2 storage (3 containers: bronze/silver/gold), a least-privilege service principal, and a single-node Databricks cluster that auto-terminates after 20 min. Databricks connects to storage via direct abfss:// + OAuth, with secrets in a secret scope (no mounts).

resource "azurerm_storage_account" "lake" {
  account_tier             = "Standard"
  account_replication_type = "LRS"      # cheapest
  is_hns_enabled           = true       # <-- this makes it ADLS Gen2 (real directories)
}
WhySingle-node = no worker-VM cost (the biggest lever). Auto-terminate stops idle burn. A service principal is scoped + rotatable (unlike account keys). Direct ABFSS is the modern pattern; mounts are legacy.
AlternativesPlain Blob (no real directories → worse Delta); multi-node cluster (overkill at 250 MB); account keys (god-mode); Portal click-ops (not reproducible → chose Terraform).
Next stepsOIDC auth instead of a token in CI; a $5 budget alert; Unity Catalog if it grows.

3 · Dual-engine, local-first design

What: every transform exists twice — a local polars + deltalake module in src/nfl/ and a PySpark notebook in databricks/notebooks/ — from one logic spec.

WhyThe dev machine has no Java (PySpark-on-Windows is painful). Polars/delta-rs runs the entire pipeline for $0 with no Java, and writes real Delta tables that Databricks can read. You build and test free locally, and only pay to prove cloud parity.
AlternativesPySpark-only (needs JDK + winutils; can't dev cheaply); Spark-in-Docker (heavy); DuckDB (fine, but polars matches the pandas/Spark model better).
Next stepsThe Databricks notebooks are currently behind the local modules (missing the newest features) — re-sync them so parity is exact.

4 · Bronze — raw ingestion (Phase 2)

What: pull 2015–present from nflreadpy, add lineage columns, and append to Delta — no cleaning.

sdf = (spark.createDataFrame(pldf.to_pandas())
       .withColumn("_ingest_ts",   F.current_timestamp())
       .withColumn("_source_file", F.lit(source_file))
       .withColumn("_batch_id",    F.lit(batch_id)))
writer.mode("append").save(path)      # Bronze is an immutable, append-only log
Concept: the Bronze contractBronze stores data exactly as delivered so history is always replayable and auditable. All business logic is deferred to Silver. Lineage columns make every row traceable to its ingestion run.
WhySeparating "capture" from "clean" means a bug in cleaning never costs you the raw data — you just re-run Silver.
AlternativesWrite straight to a cleaned table (loses the audit trail); CSV/Parquet without Delta (no ACID/time-travel).

5 · Silver — clean, validate, conform (Phase 3)

What: dedupe; drop special-teams/garbage-time/null-possession plays; impute dome weather; conform team identity across relocations (SD→LAC, STL→LAR, OAK→LV); run a data-quality gate that hard-fails before writing; Z-ORDER for fast reads.

# keep only real offensive plays; drop garbage time; one predicate does a lot
.filter(((pl.col("pass")==1)|(pl.col("rush")==1)) & (pl.col("special").fill_null(0)==0))
.filter(pl.col("epa").is_not_null())
Concept: data-quality gateA lightweight "Great Expectations"-style suite — unique, not_null, in_range — that raises an error before a bad write. It literally caught a real bug: a franchise-relocation mismatch was creating duplicate game rows (the unique(game_id) check failed).
WhyTeam conforming is essential — otherwise home/away joins break and Elo treats a relocated team as two franchises.
Next stepsRow-count/freshness drift checks; quarantine bad rows instead of hard-fail for non-critical checks.

6 · Gold — leakage-safe features (Phase 4 + Tier 2) most important

What: one row per game with home-vs-away feature deltas and target labels. Features: rolling EMA of off/def EPA, CPOE, turnovers; Elo; rest; travel; injury index + QB-out; continuous QB value; opponent-adjusted EPA.

Concept: data leakage & the shift(1) trickA feature on a game's row may use only info available before kickoff. We compute a rolling average of a team's form, then shift it forward one game so a row never sees its own result:
pl.col("off_epa").ewm_mean(span=8).shift(1).over("team")   # EMA of PRIOR games only
# Self-test: 2015 Week-1 rows have NULL features (no prior games exist) ✔

Elo is recorded before updating (pre-game snapshot), iterating in date order:

eh, ea = ratings[home], ratings[away]           # snapshot BEFORE the game
rows.append((game_id, eh, ea))                  # <- this is the leakage-safe feature
if played:                                      # update only AFTER recording
    exp = 1/(1+10**((ea-eh-HFA)/400)); ratings[home] += K*(actual-exp)
Concept: opponent-adjusted EPARaw EPA is confounded by schedule (great stats vs. weak defenses mean less). We subtract the opponent's pre-game strength from each game's EPA, then roll — so ratings are net of who you played.
Concept: continuous QB valueA QB-out flag is crude. We give each starting QB a rolling passing-EPA value (replacement level for backups) and feed the home-minus-away difference — the single biggest swing in team strength.
AlternativesFull ridge/mixed-effects opponent adjustment (heavier; research shows only ~0.5% gain) → chose the one-pass version; QB Elo (richer but complex) → chose rolling passing-EPA proxy.
Next steps — known limitationRolling features are keyed to a game's own play-by-play, so future games have null features (live picks use only spread+Elo+injuries). Fix: carry each team's most-recent form forward to its next scheduled game. Also: success rate, early-down EPA, pass-rate-over-expected, pace.

7 · MLOps — training & walk-forward CV (Phase 5)

What: LightGBM + XGBoost on three targets (win, cover, margin); every run logged to MLflow (params, metrics, feature-importance plots, model artifacts); best model aliased champion; Vegas logged as a baseline.

Concept: walk-forward validationTime-series data must be split by time. We train on seasons [N-4, N-1] and test on season N, rolling forward. Random k-fold would train on 2024 to predict 2019 — training on the future — and inflate scores.
for test_season in range(FIRST, LAST+1):
    train = df.filter(season.is_between(test_season-4, test_season-1))
    test  = df.filter(season == test_season)        # always strictly future
Why GBDTs, not deep learningWide/small tabular data → gradient-boosted trees win: fast, no GPU, handle missing values natively, and give free feature-importances. A neural net would cost more and lose.

Result: win AUC 0.669 — which was worse than the Vegas line (0.724) the model already ingests. That diagnosis drove the next step.

8 · Market-anchored distributional model (Phase 5.5) the big lever

The key insightThe plain model was diluting an already-efficient market signal. A trivial baseline — the spread run through a bell curve — scores ~0.72 AUC with zero machine learning. So the fix wasn't more features; it was to anchor to the market and only deviate on real signal.

What: predict the residual (actual_margin − spread_line), assume margin ~ Normal(μ, σ≈12.8), and derive both win and cover probabilities analytically:

mu = spread_line + SHRINK * model.predict(X)      # anchor to line + shrunk deviation
win_prob   = Φ(mu / sigma)                        # Φ = normal CDF
cover_prob = Φ((mu - spread_line) / sigma)
ModelWin AUCBrier (lower=better)
Baseline GBM0.6690.230
Market-anchored0.714 → 0.717 (+Tier2)0.213
Vegas ceiling0.7260.211
Concept: calibrationFor betting, calibration (a 70% pick wins 70% of the time) matters more than ranking (AUC). We measure Brier and log-loss and fit isotonic regression on a held-out season.
Honest findings & next stepsStill does not beat the pure spread baseline (the ceiling). Isotonic calibration on one small season slightly hurt — next: pool more seasons / Platt scaling; learn σ (heteroscedastic); confidence-weighted SHRINK.

9 · Honest betting evaluation (Phase 5.6)

Concept: accuracy ≠ profitA model can be accurate and still lose money to the "vig" (the house's cut). The real test is a betting backtest: simulate wagering and measure ROI.

10 · CI/CD & tests (Phase 6)

What: GitHub Actions runs ruff (lint) + pytest on every push; a gated job deploys a Databricks Asset Bundle on the main branch. Tests target the correctness invariants.

def test_ema_shift_is_leakage_free():
    out = s.with_columns(pl.col("x").ewm_mean(span=4).shift(1).over("team").alias("ema"))
    assert out["ema"][0] is None     # first game has no prior -> must be null
Why these testsThey lock down the things that silently corrupt results if broken: a leaky window, a mis-mapped relocated team, bad odds math. Fast, deterministic, no data download.

11 · Post-mortem lessons (real Week 5)

Model went 9/15 (60%). Diagnosis:

  • 🎲 High-variance upset week — the Vegas favorite lost 5/15 (33% vs. ~25% baseline). Vegas also "lost many."
  • 4 of 6 misses were genuine upsets no model catches (TB beat a 9.5-pt favorite — a ~2.5σ event).
  • 🎯 Catchable pattern: in 2 misses our own Elo favored the winner, but market-anchoring overrode it → idea: deviate more when power ratings strongly disagree with the line.
  • 📏 One week (15 games) can't judge a model — 60% in a 33%-upset week is statistically normal.
